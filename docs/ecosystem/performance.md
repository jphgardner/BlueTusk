# Ecosystem performance qualification

`ecosystem-performance.yml` is a manually dispatched, exact-commit local capacity gate for Jobs, Workflows, Projections and Documents. Dispatch it with a full 40-character `candidate_sha` that already contains this workflow, the budget contract and verifier, and type `RUN-ECOSYSTEM-PERFORMANCE`. It requires a clean checkout on the dedicated Windows Ryzen 7 5800X benchmark runner, Docker in Linux-container mode, Python and .NET from `global.json`. The workflow has read-only repository permissions and performs no packaging, release or publication step.

The gate runs **two independent campaigns** of each workload. Each Jobs/Workflows storage campaign offers 30 minutes per product with seeded high-entropy payloads. Projections runs separate 30-minute steady-load and overload profiles per repetition; Documents fixed-cardinality churn also runs for 30 minutes. The wall time is several hours because campaigns are sequential and include setup, drain, recovery and verification. Each harness uses a dedicated disposable PostgreSQL fixture. The gate checks each completed campaign immediately and rejects missing runs, wrong payload mode, failed logical/recovery checks, insufficient measurement time or sparse storage/service observations. A successful pass means only that this workload and runner met the explicit local thresholds below. It does not establish production capacity, indefinite storage bounds or performance leadership.

| Workload | Minimum throughput | Maximum p99 | Storage ceiling |
| --- | ---: | ---: | ---: |
| Jobs | 20 durable completions/s | 10 s hot, 3 s cold | 64 MiB runtime relations; 2 MiB/min late net growth; 64 KiB cluster WAL/accepted |
| Workflows | 5 durable completions/s | 30 s hot, 12 s cold | 128 MiB runtime relations; 4 MiB/min late net growth; 256 KiB cluster WAL/accepted |
| Projections steady load | 20 scheduled offers/s; 19 accepted/s; 18 inbox effects/s during offering; ≥99% admission and ≥95% inbox coverage by offer end | 1 s commit, 2 s projection/inbox, 3 s Live coverage; ≤60 s drain | 2 GiB owned storage, 256 MiB retained slot, 256 KiB WAL/committed operation |
| Projections overload | 30 committed operations/s with bounded admission, rejection and final-half progress for every tenant | 5 s commit; projection/inbox p99 observed but not constrained as an interactive SLA | 4 GiB owned storage, 2 GiB retained slot, 256 KiB WAL/committed operation |
| Documents | 500 committed transitions/s | 500 ms save | 1 GiB peak owned relations, 16 MiB/min late owned growth, 8 GiB whole database, 64 MiB/min late whole-database growth, 64 KiB WAL/transition |

The exact numeric contract, minimum durations, fixture resource guardrails and PostgreSQL image digests are in [`eng/ecosystem-performance-budgets.json`](../../eng/ecosystem-performance-budgets.json). These are provisional qualification thresholds, **not measured 30-minute claims**. The gate must actually run and pass on a committed candidate before reporting success. Jobs/Workflows late growth uses the final-half endpoint rate and physical relation peak from the raw sample stream. Their WAL budget divides the PostgreSQL cluster's before/after WAL-position delta by accepted work, so the fixture must stay dedicated during each campaign. The Documents sustained scenario must attest `AttachedContent` storage; its verifier also requires the 15-cell inline JSONB sweep, distinct stable payloads, hard-kill recovery, maintenance coverage and disk headroom. The 1 GiB owned-relation check includes detached content, while the whole-database cap covers the entire disposable database. Projections verifies exact pipeline state, the steady profile's admission and end-of-offer delivery, profile-appropriate p99s, ten-second physical samples, retained-slot and owned-storage peaks, and WAL per committed operation. The historical `TransactionsPerSecond` report field counts committed operations over pipeline time; a seeded overload transaction may contain several operations.

Each artifact retains raw harness reports, workload logs, fixture observations, before/after source captures, runnable harness binary snapshots, Documents scoped source snapshots and bindings, a budget snapshot, and a manifest containing the full candidate SHA and SHA-256 of every retained file. The gate builds once, runs the captured binaries without rebuilding and verifies their live hashes after each campaign. The offline verifier checks the artifact hashes again and repeats the budget checks. Git cleanliness and before/after source-tree hashes bind all campaigns to the same commit; the Jobs source fingerprint and Documents executable bindings add harness-specific checks. The archived evidence has a 90-day GitHub Actions retention period.

Windows benchmark-runner capacity, Docker CPU/memory throttling, PostgreSQL version and workload distribution limit comparisons with real deployments. Jobs/Workflows currently support at most one hour per product invocation; this gate uses half-hour repeats, not a continuous multi-hour single invocation. Projections' overload profile seeds 10,000 pending operations and schedules 1,500 offers/s against a much lower delivery capacity, so offered-to-projection and offered-to-inbox p99 include queue age and are not interactive latency claims. Its 30-minute Live replay window, permanent Events identities/outbox/inbox, and finite 30-minute owned-storage ceiling do not establish a storage plateau. Documents uses the existing bounded physical-space guard. Longer isolated endurance, multi-host fleets, representative data and production operating limits remain separate release work.
