# Documents TOAST maintenance profiler diagnostics

The updated Documents load harness was built in Release with zero warnings and run against four separate, labelled PostgreSQL 18 Docker fixtures on 27 September 2026. Every fixture used a unique database volume and generated schema; each run ended with zero owned schemas and no labelled Documents container or volume. The two successful diagnostics each verified all 15 payload/tenant/concurrency cells and the sustained cell, including a hard-killed transaction child and exact acknowledged-write recovery. These are short functional and instrumentation checks, not a storage-performance comparison. Whole-tree candidate source changed during each run as other product work proceeded; the before/after scoped Documents, Data, TypeSystem and harness sources stayed unchanged according to each [binding report](maintenance-diagnostic-default/bindings.json).

| [ToastVacuumFast](maintenance-diagnostic-tuned/documents-load.json) | 226,320,384 | 226,148,352 | 234,714,815 | 1,005,454,245,888 | 2 |

The direct TOAST size is contained in the parent relation's `pg_total_relation_size`; these columns must not be added. The tuned fixture reported both actual parent and TOAST reloptions (`autovacuum_vacuum_scale_factor=0.01`, `autovacuum_vacuum_threshold=50`, `autovacuum_vacuum_cost_delay=0`, `autovacuum_vacuum_cost_limit=2000`). These are experimental settings applied only to a generated fixture table and its TOAST child. BlueTusk package and PostgreSQL defaults remain unchanged. The short diagnostics had different write counts and whole-tree activity, so their throughput, latency and byte totals do not establish a tuned benefit. The default fixture recorded one TOAST autovacuum during its ten-second idle observation; the tuned fixture recorded none in that short interval.

The [impossible headroom run](maintenance-guard-headroom/documents-load.failure.json) stopped before any completed cell: 1,006,897,520,640 bytes were available versus 1,099,511,627,776 required. The [16 MiB database-cap run](maintenance-guard-database/documents-load.failure.json) stopped after five completed cells at 25,138,879 observed database bytes versus a 16,777,216-byte cap. The cap check follows bounded seed batches or a five-second timed interval, so this observed overrun is not an exact hard disk quota. Its failure sidecar retained the parent and TOAST relation IDs and sizes, filesystem headroom, source fingerprint and DLL hashes. Both intentional failures exited nonzero, recorded `failed` binding status, matched all ten measured DLLs to pre-run snapshots, and cleaned up their owned resources.

The runbook defaults to a 24 GiB database-size stop and 8 GiB minimum observed filesystem availability, sampled by a separate label-checked Docker observer once a second. The harness checks fresh samples and the database bound during work; missing or stale filesystem observations fail closed. The observed host had more than 1 TB available during these checks, and a completed default profile previously reached 16.1 GB by 600 seconds. A full 600-second default/tuned pair is therefore feasible under the named resource stops, but either may stop early and must then be reported as a guarded failure. The original [16.1 GB default-profile baseline](../2026-09-27-pg18-baseline/README.md) remains the unresolved storage-growth result. A quiet, source-frozen full pair and repeat runs are still needed before making any maintenance or throughput claim.

Raw [default](maintenance-diagnostic-default/documents-load.json) and [tuned](maintenance-diagnostic-tuned/documents-load.json) reports, all four binding reports, final filesystem samples and schema-cleanup counts are retained in this directory. Exact runnable dependencies and before-run source snapshots remain in the ignored local `artifacts/documents-load/maintenance-*` directories. The fixture watcher and workload do not log document payloads or connection passwords.
