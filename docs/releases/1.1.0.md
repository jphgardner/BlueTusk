# BlueTusk 1.1.0 release notes

> **Not published yet.** `1.1.0` is in release qualification. Until it is
> published, the latest packages are `1.0.0` (stable) and `1.1.0-rc.1`
> (release candidate). This page describes what `1.1.0` will contain, based on
> the `main` branch.

BlueTusk 1.1.0 re-releases every Core family on one version line: Provider
(ADO.NET, EF Core, extensions, cloud identity and the `bluetusk` tool),
Streams, Sync, Live and Control Plane. It keeps the 1.0 public API: code
written for 1.0.0 compiles against 1.1.0.

When 1.1.0 is published, `1.0.0` and `1.1.0-rc.1` will be deprecated on NuGet
and npm and will point to `1.1.0`.

## Not in this release

- **Graph (SQL/PGQ) and Continuous Graph** stay in preview. PostgreSQL removed
  SQL/PGQ in PostgreSQL 19 Beta 4, so these wait for a PostgreSQL release that
  ships it. See the [Graph guide](../graph/README.md).
- **Ecosystem families** (Events, Jobs, Workflows, Documents, Schema,
  Projections, Search, Sql, Studio and Edge) are `0.1.0-preview.1` and are
  released separately when their own checks pass.

## What is new since 1.1.0-rc.1

None of these are in `1.0.0` or `1.1.0-rc.1`.

### Provider

- **Native REPACK** for PostgreSQL 19 (preview server): run `REPACK` and
  watch its progress from .NET with `RepackAsync` in
  `BlueTusk.Data.Maintenance`. See [Native REPACK](../ado-net/repack.md).
- `BlueTuskDataReader.GetFieldByteLength` and `GetPostgreSqlTypeOid`.
- **`bluetusk doctor`** checks a server before you deploy: version, TLS,
  logical replication settings and required extensions. See the
  [tool README](../../tooling/BlueTusk.Tool/README.md).
- **Production template.** `dotnet new bluetusk-production` from the new
  `BlueTusk.Production.Templates` package creates a complete application. See
  the [template README](../../templates/BlueTusk.Production/README.md).

### EF Core

- **`SaveChanges` batching.** Inserts, updates and deletes are now sent in
  batches of up to 42 statements per round trip. In 1.0.0 and 1.1.0-rc.1 each
  statement was its own command. To change the batch size, use EF Core's
  standard `MaxBatchSize` option. See [EF Core concepts](../ef-core/concepts.md).
- **Complete store values.** `GetCompleteDatabaseValues()` and
  `GetCompleteDatabaseValuesAsync()` read an entity's current database values
  including its complex collections, which EF Core's `GetDatabaseValues()`
  leaves out. See
  [reading current database values](../ef-core/concepts.md#read-the-current-database-values-including-complex-collections).

### Sync

- New destinations:
  - `BlueTusk.Sync.Kafka` writes each source transaction and its checkpoint
    in one Kafka transaction.
  - `BlueTusk.Sync.S3` writes compressed Parquet files and a commit manifest
    to S3-compatible storage.
  - `BlueTusk.Sync.Webhooks` sends signed HTTP requests.

  See [Sync configuration](../sync/configuration.md).

### Live

- New browser packages `@bluetusk/live-vue` (Vue 3) and
  `@bluetusk/live-svelte` (Svelte 5).
- The browser client batches incoming events before it updates your UI
  (`maximumBatchEvents`, default 64).
- `LiveSharedSubscriptions` and `LiveSharedSubscription.ResetAsync` for
  shared subscriptions.

### Control Plane

- **Fleet operations**: deployment inventory and audited pause, resume,
  reconcile, rebuild and delete operations.
- **Kubernetes operator** in the new `BlueTusk.ControlPlane.Kubernetes`
  package.
- Dashboard options `BrandLabel` and `DataProvenanceNotice`.

## Fixes since 1.1.0-rc.1

These defects were found while writing and running the documentation
samples. They are fixed in 1.1.0 and are present in 1.0.0 and 1.1.0-rc.1.

### Provider

- `ExecuteScalarAsync<T>()` converts with the same rules as
  `GetFieldValue<T>()`. `ExecuteScalarAsync<decimal>()` on a `numeric` result
  no longer throws `InvalidCastException`, and nullable targets such as
  `decimal?` work.
- **Behaviour change:** a full connection pool no longer waits forever. The
  connection-string `Timeout` (default 15 seconds) now also limits the wait for
  a free pooled connection. When it expires, opening throws a
  `TimeoutException` that names the endpoint, `Maximum Pool Size` and
  `Timeout`. A cancellation token still cancels the wait earlier. If your
  application relied on unlimited waits, raise `Timeout`. See
  [connection pooling](../ado-net/pooling.md).
- Unknown connection-string keywords are still ignored by default, to stay
  compatible with 1.0.0. To reject them, as Npgsql does, turn on the
  `BlueTusk.Data.RejectUnknownConnectionStringKeywords` AppContext switch.
  Rejection is planned as the default for 2.0. See
  [ADO.NET configuration](../ado-net/configuration.md).
- A data source that maps a type with `MapEnum` or `MapComposite` can connect
  before the type exists, so an EF Core migration can create it. `Migrate`
  and `MigrateAsync` reload the type catalogue afterwards.

### EF Core

- Enum constants in LINQ queries use the mapped PostgreSQL label
  (`[BlueTuskName]`, then `[EnumMember]`) instead of the C# member name.
- `Contains` over a collection parameter works with
  `ParameterTranslationMode.Parameter`. The collection is sent as one typed
  PostgreSQL array.

### Streams and Sync

- A change stream without a delivery observer now confirms each acknowledged
  position to PostgreSQL, so the replication slot releases WAL. Before, a
  hosted consumer or direct Sync pipeline without an observer kept all WAL
  until the slot was dropped.
- Checkpoint and relay observers renew their lease on a timer, so an idle
  consumer or a slow destination keeps ownership.
- The PostgreSQL Sync destination retries transient failures (lost
  connections, serialization failures and deadlocks) instead of stopping the
  pipeline on the first error.

### Live

- The `@bluetusk/live` browser client no longer fails with "Illegal
  invocation" when you do not pass your own `fetch`.

## Changes since 1.0.0

1.1.0 also includes everything from
[1.1.0-rc.1](1.1.0-rc.1.md), which focused on performance across all
families:

- **Provider**: faster, lower-allocation command and reader paths.
- **Streams**: less copying of transaction data and reuse of assembly state.
- **Sync**: smaller NATS messages, streamed OpenSearch bulk requests and
  binary PostgreSQL apply.
- **Live**: snapshot updates limited to affected keys, and batched Angular and
  React updates.
- **Control Plane**: set-based inventory, limits on concurrent instance calls
  and a cached, source-generated API.

## Upgrade from 1.0.0 or 1.1.0-rc.1

1. Change every BlueTusk package, and every `@bluetusk/*` npm package, to the
   same new version. Do not mix versions. See
   [Install BlueTusk](../getting-started/install.md).
2. EF Core applications: `SaveChanges` now batches statements. If something
   depends on one statement per round trip, set `MaxBatchSize(1)` to restore
   the old behavior.
3. ADO.NET applications: opening a connection from a full pool now fails
   after the connection-string `Timeout` (default 15 seconds) instead of
   waiting forever. Raise `Timeout` if you need longer waits.
4. Rebuild and run your tests against each PostgreSQL version you use.
5. Follow the [upgrade guide](../operations/upgrade-guide.md) for the
   deployment order and rollback plan.
